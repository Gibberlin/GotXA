GOTXA FRONTEND API INTEGRATION CONTRACT
========================================

Purpose
-------
This file is the frontend team's API handoff for GotXA. It lists the APIs exposed by the backend, Corporate Portal, SCADA gateway, and log collector; explains what each endpoint does; and identifies demo/fallback behavior that must be removed from frontend code.

The API gateway is the normal browser entry point:

  http://localhost/

The gateway routes requests to the backend and frontend services. In production, replace localhost with the deployment hostname.

IMPORTANT IMPLEMENTATION RULES
------------------------------
1. Use live API responses as the source of truth. Do not keep hardcoded dashboard metrics, alerts, incidents, machines, alarms, tasks, users, or activity arrays in the frontend.
2. Do not treat HTTP 200 as proof that data is live. Some current backend routes return demo fallback data when a dependency is unavailable. The frontend should display a degraded/offline state when a response contains fallback data or when a service returns an error.
3. Preserve IDs exactly as returned by the API. Alert database IDs and public alert_id values are different; use the `id` field for update/detail routes unless the endpoint specifically asks for alert_id.
4. Send JSON with `Content-Type: application/json` for JSON requests.
5. Store the returned access token in memory or a secure application session mechanism and send it as `Authorization: Bearer <access_token>` on authenticated requests.
6. The backend also accepts `X-User-ID`, but that is a development/demo fallback. Do not use it as production authentication.
7. Use the gateway paths in browser code. Direct service URLs are for internal Docker communication, diagnostics, or local service testing only.

STANDARD RESPONSE SHAPES
------------------------
Most SIEM/SOAR endpoints use this success wrapper:

  {
    "data": <object or array>,
    "message": "Success",
    "timestamp": "2026-09-14T12:00:00.000000",
    ...optional top-level copies of object fields...
  }

Paginated endpoints return a `data` object like:

  {
    "items": [],
    "total": 0,
    "page": 1,
    "page_size": 25,
    "pages": 0
  }

Errors use:

  {
    "error": {
      "code": "BadRequest|Unauthorized|Forbidden|NotFound|InternalError",
      "message": "Human-readable explanation",
      "details": {}
    }
  }

HTTP status meanings:
  200  Successful read/update
  201  Resource created
  202  Accepted for processing or playbook execution
  204  Successful logout with no response body
  400  Invalid request
  401  Missing/invalid authentication
  403  Authenticated but not authorized
  404  Resource not found
  409  Invalid lifecycle transition or conflict
  422  SCADA value rejected by safety range
  500/503  Service or dependency failure

AUTHENTICATION AND ROLES
------------------------
SIEM/SOAR login:

  POST /api/auth/login

Request:
  {
    "username": "admin",
    "role": "admin"
  }

Response data:
  {
    "user": {
      "id": "...",
      "username": "admin",
      "email": "admin@gotxa.local",
      "role": "admin"
    },
    "access_token": "gotxa_sess_...",
    "expires_at": "...",
    "session_id": "..."
  }

Corporate Portal login is separate and returns the same style of session token:

  POST /api/corporate/auth/login

Request:
  {
    "username": "admin",
    "password": "password456"
  }

Response:
  {
    "user": { "id": "...", "username": "admin", "name": "...", "department": "..." },
    "access_token": "gotxa_sess_...",
    "expires_at": "...",
    "session_id": "..."
  }

Send the returned token as:
  Authorization: Bearer gotxa_sess_...

Supported role permissions:
  admin        Full read/write, playbooks, containment, settings, reports, audit
  soc_manager  Alerts/incidents/playbooks/containment/reports; no settings write
  analyst      Read alerts, create/edit incidents; no playbooks, settings, or reports

SCADA FRONTEND FALLBACK WARNING
-------------------------------
The backend proxy currently returns simulated telemetry/machine/alarm values when the SCADA gateway is unavailable. The frontend must display `degraded` or `offline` and must not present fallback telemetry as real plant state. Remove hardcoded values from frontend bundles and use the actual response status.

FRONTEND DEMO/FALLBACK DATA TO REMOVE
-------------------------------------
Remove or replace these patterns from frontend code:

1. Hardcoded SIEM metrics such as total_transactions=1234, response_time=38, or security_score defaults.
2. Hardcoded alert/incident arrays and synthetic source/attack events.
3. Fake report objects created locally instead of calling POST /api/reports and downloading the returned URL.
4. Local fallback machine values such as refinery temperature=182.4 or flow_rate=54.8 when the gateway is down.
5. Local default alarm lists and fake command success messages.
6. Corporate Portal SYSTEMS, TASKS, ANNOUNCEMENTS, and ACTIVITY demo arrays once persistent endpoints are available.
7. Client-side “success” messages after a failed network request. Show the server error and preserve the failed state.
8. Direct `http://localhost:5002` URLs in browser code. Use gateway paths so deployment hostnames work.
9. Use of `X-User-ID: admin` in production. Use the returned Bearer token.
10. Treating `status: 200` from a compatibility endpoint as real enforcement. For SOAR, inspect execution status and outputs.enforcement.

RECOMMENDED FRONTEND API CLIENT
--------------------------------
Every frontend should use one shared request helper:

  async function apiRequest(path, options = {}) {
    const token = sessionStorage.getItem('gotxa_access_token');
    const response = await fetch(path, {
      ...options,
      headers: {
        'Content-Type': 'application/json',
        ...(token ? {Authorization: `Bearer ${token}`} : {}),
        ...(options.headers || {})
      }
    });
    const body = response.status === 204 ? null : await response.json();
    if (!response.ok) {
      throw new Error(body?.error?.message || `Request failed: ${response.status}`);
    }
    return body;
  }

For every dashboard:
  - Load authentication/user state first.
  - Load capabilities before rendering action buttons.
  - Use AbortController for polling cleanup.
  - Show loading, empty, degraded, unauthorized, and error states.
  - Stop polling after logout.
  - Never put bearer tokens in URLs or logs.

MINIMUM INTEGRATION ORDER
-------------------------
1. Login: POST /api/auth/login or /api/corporate/auth/login.
2. Current user: GET /api/auth/me or /api/corporate/me.
3. Permissions: GET /api/capabilities.
4. SIEM overview: GET /api/overview and /api/overview/metrics.
5. Alerts: GET /api/alerts and GET /api/alerts/<id>.
6. Incidents: GET /api/incidents and GET /api/incidents/<id>.
7. Live event stream: GET /api/raw-stream.
8. SCADA state: GET /api/scada/machines and GET /api/modbus*.
9. Corporate state: GET /api/corporate/dashboard, /systems, /tasks, /announcements.
10. Mutations only after capability checks: status changes, suppressions, assignments, commands, playbooks, reports.

KNOWN BACKEND CONTRACT NOTES
----------------------------
- The backend registers several legacy and consolidated route families. New frontend work should prefer the canonical routes in this file and avoid adding more aliases.
- Corporate Portal task/system/announcement data is currently stored in process memory in api_corporate.py. It will reset when the backend restarts; the frontend should not treat it as durable until persistence is implemented.
- Saved views currently return a compatibility response and are not persisted. Do not present them as durable user configuration without implementing storage.
- Some reporting and detection-rule endpoints contain placeholder values or dry-run behavior. Label them accordingly until their services are connected to real storage/execution.
- Real IP blocking requires SOAR_REAL_MODE=true, the backend NET_ADMIN capability, and the iptables-enabled backend image. The response reports whether enforcement was real or simulated.
- SCADA emergency containment is represented in the current SOAR implementation and must be reviewed before production use; never silently execute dangerous plant actions from a frontend click.
- Attack simulation endpoints and scripts are for the authorized GotXA lab only.
