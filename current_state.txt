## BACKEND ARCHITECTURE

### Database Layer (SQLAlchemy ORM)
**Models:** (`app/models.py`)
- `User`: User accounts, roles, teams, permissions
- `Team`: Team organization
- `Alert`: Security alerts with suppression, assignment, entities, MITRE mappings
- `Incident`: Incident management with workflow (open→investigating→contained→resolved→closed)
- `Task`: Incident tasks with assignment and due dates
- `Evidence`: Digital evidence storage (files, screenshots, logs)
- `PlaybookExecution`: SOAR playbook tracking with approval workflow
- `AuditEvent`: Immutable audit log (correlation ID, actor, action, resource, change, reason, IP, user agent)
- `Setting`: Configuration key-value storage with sensitivity flags
- `SettingChange`: Historical tracking of all setting changes with approval workflow
- `Report`: Generated reports (NIST, Executive, Coverage, Post-Incident)

**Indexes:** All frequently-queried fields indexed (host, level, severity, status, user_id, created_at)

### Authentication & RBAC (`app/auth.py`)
**Roles:**
- `admin`: Full access to all actions
- `soc_manager`: Can execute playbooks but not approve (escalation)
- `analyst`: Can create/investigate incidents but not close or execute playbooks

**Permissions Matrix:**
- alerts.view, alerts.assign, alerts.suppress
- incidents.create, incidents.edit, incidents.close, incidents.assign
- playbooks.execute, playbooks.approve
- containment.execute, containment.approve
- settings.read, settings.write, settings.approve
- reports.generate, audit.view, users.manage

**Decorators:**
- `@authenticate`: Validates user from Bearer token or X-User-ID header
- `@require_permission(action)`: Enforces RBAC before action
- `AuthContext`: Per-request auth context with team-based access control

### Audit Logging (`app/audit.py`)
**AuditLogger:**
- Immutable event log with correlation IDs
- Tracks actor, action, resource, before/after state, reason, IP, user agent
- High-risk settings automatically flagged for approval
- All mutations logged (alert.assigned, incident.created, playbook.executed, setting.changed)

## IMPLEMENTED ENDPOINTS (8 GROUPS)

### 1. CORE READ APIs ✅
- `GET /overview` - KPI cards, charts, priority queue, source health
- `GET /dashboard-data` - Legacy dashboard (backward compatible)
- `GET /raw-stream?limit=&cursor=` - Cursor-based log pagination (max 250/page)
- `GET /alerts?severity=&status=&assignee=&sort=&order=&page=&page_size=`
- `GET /alerts/{alert_id}` - Full alert context
- `GET /alerts/{alert_id}/investigation` - Investigation context (timeline, entities, MITRE, IOCs, related alerts)
- `GET /incidents?status=&priority=&owner=&page=&page_size=`
- `GET /incidents/{incident_id}` - Full incident details

### 2. ALERT ACTIONS ✅
- `POST /alerts/bulk-assign` - Assign multiple alerts (idempotent)
- `POST /alerts/{alert_id}/suppress` - Suppress alert with expiration and scope (alert/rule/entity)

### 3. INCIDENT WORKFLOW ✅
- `POST /incidents` - Create new incident (with alert linkage)
- `PATCH /incidents/{incident_id}` - Update with state validation
  - Valid transitions enforced (open→investigating→contained→resolved→closed)
  - Closure requires reason, notes
  - Returns 409 for invalid transitions
- `POST /incidents/{incident_id}/tasks` - Create task
- `POST /incidents/{incident_id}/merge` - Merge incidents (idempotent)
- `POST /incidents/{incident_id}/split` - Split incident
- `POST /incidents/{incident_id}/evidence` - Add evidence

### 4. SOAR & RESPONSE ✅
- `POST /playbooks/{playbook_id}/executions` - Execute playbook
  - Returns 202 Accepted (async)
  - High-risk playbooks (isolation, firewall, user_disable) require approval
  - Dry-run mode available
- `GET /playbook-executions/{execution_id}` - Check execution status
- `POST /playbook-executions/{execution_id}/approve` - Approve high-risk execution
- `POST /playbook-executions/{execution_id}/rollback` - Rollback execution
- `POST /containment-requests` - Request immediate containment action

### 5. DETECTION ENGINEERING ✅
- `POST /detection-rules/{rule_id}/test` - Test rule in safe environment
- `GET /detection-rules/{rule_id}/versions` - Version history
- `POST /detection-rules/{rule_id}/rollback` - Rollback to previous version
- `PATCH /detection-rules/{rule_id}` - Update rule

### 6. REPORTING, ASSETS, ACCESS ✅
- `GET /assets?zone=&criticality=&health=&page=&page_size=`
- `GET /assets/export?format=csv|xlsx` - Export assets
- `POST /reports` - Generate report (returns 202)
- `GET /reports/{report_id}/download` - Download report
- `POST /saved-views` - Save custom view/filter
- `GET /saved-views` - List saved views
- `GET /access/review` - Access audit review
- `GET /evidence/{evidence_id}` - Get evidence

### 7. SETTINGS & CONFIGURATION ✅
- `GET /settings/overview` - All settings (masked if sensitive)
- `GET /settings/{section}` - Settings by section
- `PATCH /settings/{section}` - Update settings
  - High-risk settings flagged (retention, disabling rules, privilege changes, OT playbooks)
  - Requires reason, change ticket, rollback plan
  - May return 202 Accepted if approval needed
- `GET /settings/history` - Change history
- `POST /settings/{section}/validate` - Validate setting
- `POST /settings/{section}/test` - Test in safe environment
- `POST /approvals` - Request approval for high-risk change
- `POST /reauthenticate` - Reauthenticate for high-risk changes

### 8. HEALTH & CAPABILITIES ✅
- `GET /capabilities` - User's available actions (based on role)
- `GET /audit-events?page=&page_size=` - Audit log
- `GET /health` - Server health check
- `GET /api/status` - API status

## SECURITY FEATURES

### Authentication
- Bearer token support (JWT ready)
- Session cookie support (X-User-ID header)
- Demo user auto-creation (admin role)

### Authorization (RBAC)
- Role-based permissions enforced server-side
- Team-based access control (users can only see their team's resources)
- Permission check on every mutation endpoint
- Escalation workflow for sensitive actions (manager approval required)

### Audit Trail
- Every mutation logged with correlation ID
- Tracks: actor, action, resource, before/after state, reason, IP, user agent
- Immutable (append-only audit table)
- Supports full incident investigation timeline

### Data Protection
- Sensitive fields masked based on permissions
- Secrets never exposed in responses
- All changes tracked with audit events

### High-Risk Actions
- High-risk playbooks (isolation, firewall, user_disable) require approval
- High-risk settings (retention, disabling rules, privilege changes, OT playbooks) require approval
- Settings changes may require reauthentication + MFA
- OT actions require two-person approval + maintenance window validation

## STATE VALIDATION & WORKFLOWS

### Alert Lifecycle
- open → suppressed, investigating, resolved, dismissed

### Incident Lifecycle (Validated)
```
open → investigating
    ↓
    → contained → resolved → closed
    ↓
    → dismissed
```
- Invalid transitions return 409 Conflict
- Closure requires: closure_reason, resolution_notes, lessons_learned
- Timestamps auto-updated: detected_at, contained_at, resolved_at, closed_at

### Playbook Execution (High-Risk)
- High-risk playbooks default to dry_run mode
- Must be approved before running in live mode
- Execution status: pending → approved → running → success/failed
- Can be rolled back with full audit trail

### Settings Changes (High-Risk)
- High-risk settings: retention, evidence_deletion, rule_disable, privilege_changes, OT playbooks
- Require: reason, change_ticket, rollback_plan
- May require reauthentication and approval
- Complete audit entry with before/after values

## DEPLOYMENT

### Docker Setup
```bash

docker compose up
```

